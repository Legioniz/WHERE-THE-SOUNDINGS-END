# Project Structure

> Project: WHERE THE SOUNDINGS END  
> Status: Connected Unity prototype with cargo, dialogue, atmospheric horror, and deep-ocean survey sandboxes  
> Owner: Project lead  
> Version: 0.6  
> Last reviewed: 2026-11-12

## Repository root

- Assets/: Unity-owned game assets and C# assemblies.
- Packages/manifest.json: pinned Unity package dependencies; Unity generates packages-lock.json.
- ProjectSettings/ProjectVersion.txt: pinned Unity Editor version.
- docs/: authoritative game design, world, narrative, technical, production, and research documents.
- tools/: offline validation and simulation utilities.
- .github/workflows/: repository integrity automation.

## Greyhaven environment generation

Run Tools > WHERE THE SOUNDINGS END > Initialize Project Foundation on first setup. It creates the initial URP assets and generates Assets/_Project/Scenes/Greyhaven_Blockout.unity.

Use Tools > WHERE THE SOUNDINGS END > Rebuild Greyhaven Environment after changing the environment generator. The command warns before replacing the generated scene. Generated Unity assets and their corresponding .meta files should be committed after successful Editor initialization.

Greyhaven is a working technical greybox. Its coordinates and dimensions are prototype scale values; final terrain, water, architecture, collision, camera framing, UI layout and interaction feel require in-Editor testing. The builder creates differentiated service fronts, residential porches, a chart table on the east T-pier, and workplace markers for the four initial residents. The chart is static and schematic; it is not a live minimap or calibrated navigation chart. The first cargo-hold interface and Harbourmaster dialogue loop are generated with the scene.

## Rules

1. Keep runtime code independent of Editor APIs.
2. Keep domain algorithms testable without scene objects where practical.
3. Store authored, mostly immutable definitions in ScriptableObjects.
4. Keep mutable world state in runtime models with clear ownership.
5. Isolate third-party assets and maintain their license records.
6. Do not commit Library, Temp, Obj, generated IDE projects, or build output.
7. Save files belong in Application.persistentDataPath and must never be committed to the repository.
8. Do not label a feature implemented until it exists in runtime code and has passed its relevant tests.


## Deep-ocean survey integration

The generated Greyhaven scene attaches a shallow DeepOceanSurveyRegion to Sheltered_Bay_Surface and gives the starter boat SoundingRigController plus close-range site inspection. Greyhaven deliberately reports no deep scattering layer. Project setup also generates OuterShoals_SurveySandbox and HollowTrench_SurveySandbox. These are functional survey test ranges, not finished levels and not connected by in-game travel.

The region component contains baseline profiles for all six named regions. The Outer Shoals and Hollow Trench profiles are attached to generated survey scenes, each with four valid site markers. The current site interaction records field-note inspection; physical vent heat, seep chemistry, brine exposure, hydrate stability, wreck entanglement, and whale-fall succession remain separate unfinished controllers.

The survey subsystem publishes through AcousticEventBus. AcousticWorldListener is connected in generated scenes: it scores signals by range, loudness, sensitivity and background noise, deduplicates event IDs, applies small sea disturbance, and exposes a SignalHeard event for future species-specific perception. No predator, fish or creature state machine subscribes yet; those listeners must be added to existing AI state machines rather than creating a parallel threat spawner.

Save schema v5 includes survey state, weather/horror timers, inspected site IDs, acoustic history and temporary atmosphere state. See [Deep-Ocean Survey Implementation](DEEP-OCEAN-SURVEY-IMPLEMENTATION.md) for the file-by-file dependency map, runtime flow, tuning assumptions and remaining integration work.
